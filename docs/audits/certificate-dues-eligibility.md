# Certificate dues eligibility audit and implementation

## Confirmed policy

The local 12 November 2026 revision permits advance payments through December and limits certificate blocking to existing, non-cancelled Monthly assessments for the current or an earlier Manila billing month. Current-month balances still count even before their due date; assessments for future billing months do not block. Penalties on included assessments count. Annual/Special charges do not block. No missing assessments are generated by eligibility checks. Personal historical obligations and the verified property-liable account are included once each. Unresolved property identity or tenant liability requires HOA review rather than a guessed account. This revision is pending separate production deployment; see [release evidence](../deployments/interface-revisions-2026-11-12.md).

Eligibility is based on the live ledger, not the Delinquent label. A full committed cash payment or approval of an existing legacy proof restores eligibility immediately; partial/pending/rejected or rolled-back amounts do not. Payment archival/restoration is reflected by the existing ledger reconciliation. No homeowner status is reset automatically.

## Enforcement and user interfaces

- Shared `CertificateDuesEligibility` service and typed validation exception.
- Homeowner and administrator request submission, approval transitions, new resident-specific previews, unissued preview-token reads and both standalone/request-bound issuance paths enforce the rule.
- Authorization/ownership checks precede eligibility details. Prepared-preview endpoints return a specific 403 for dues denial rather than misreporting an expired token.
- Existing property mutex is acquired before certificate resident/financial locks. The optional locking liability resolver and ordered obligation reads use current MariaDB values after waiting for another transaction.
- Existing requests are not rejected or rewritten automatically. Notes/rejection remain available. Issued certificate access, historical documents, source review and informational guidance remain unchanged.
- Homeowner, Admin and Staff request forms and certificate preparation show EN/FIL eligibility notices. Blocked operations use existing SweetAlert styling and visible validation without success feedback. The legacy portal request form shows the same notice and its existing validation feedback.

## Separate pre-existing findings

`AdminServiceRequestCreationTest` expects a workflow email for an Inactive account. The existing `WorkflowMail::eligible()` intentionally requires an Active, verified homeowner for workflow emails; the audit reproduced that assertion failure before this implementation and again afterward. No notification policy or existing assertion is changed here.

Five source/rendering prerequisites were skipped in the broad run. Tests requiring the configured licensed Cohabitation font/source remain skipped where unavailable; no substitute font, source auto-approval or production configuration change is introduced.

No production test request, certificate, payment, email or SMS is created for this work. Existing queued/failed jobs and financial records are outside the rollout's mutation scope.

## Local verification follow-up — 2026-11-10

The findings above describe the original feature rollout. The outdated email assertion is now corrected in tests, without changing `WorkflowMail` eligibility or production delivery policy. Admin creation for an Inactive resident remains covered; the UI asserts durable queued intent. New delivery-job tests exercise Active/verified delivery, suppression for six ineligible states, Staff alerts, repeated-event identity, duplicate job execution, after-commit dispatch and rollback.

The guarded local runner `scripts/run-readiness-gap-checks.mjs` supplies the existing licensed Windows Arial font through child-process configuration only. SQLite certificate/payment/email regressions passed: **187 tests, 1,501 assertions, zero skips**. Both previously skipped Cohabitation cases executed with their existing synthetic source fixtures; no official source or production font configuration changed.

MariaDB tests run on a fresh loopback-only temporary instance and uniquely named disposable database, with destructive-test opt-in and existing bootstrap guards. Initial runs exposed a Windows test synchronization race: Symfony's initial process status read can consume an already-emitted READY marker before the `waitUntil` callback. The tenant test now uses accumulated output and a bounded wait, retaining its real property-lock and stale-relationship assertions. This is a test-harness correction, not a runtime locking change. The final MariaDB rerun passed **six tests, 38 assertions, zero skips**: all three formerly skipped tenant cases and all three certificate-dues races. The temporary instance shut down normally.

Tooling: **16 tests passed**. PHP formatting checks passed. Full commands, exact formerly skipped case names, prerequisites and evidence boundaries are in `docs/testing/readiness-gap-checks.md`. These tests fake delivery; SMTP acceptance, inbox receipt and email-client rendering remain unverified by this follow-up. No runtime deployment is required.
